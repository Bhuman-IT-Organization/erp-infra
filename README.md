# erp-infra

Nginx, Compose, env files and CI for every customer and every environment (ADR-0007: configuration lives apart from code; ADR-0012: one isolated stack per customer per environment). Today only the **local stack** exists, because there is no machine to deploy to yet: the client's host is shared cPanel, not a VPS (ADR-0024), and wave minus one (lift and shift onto a dedicated machine) has not happened.

## The local stack

```bash
node scripts/local-up.mjs      # bring everything up
node scripts/local-down.mjs    # stop it (add --volumes to also drop the legacy database)
```

`node scripts/local-up.mjs` brings up `legacy`, `legacy-db`, `api`, `worker`, `web`, `nginx`, `redis` and `mailpit` as Compose project `erp-local` from `compose/local.yml`. It checks Docker is running, runs the legacy stack's `setup.mjs` if its credentials do not exist yet, renders the env files, runs `docker compose -f compose/local.yml up -d --build`, checks the legacy database holds a completed import, activates the `erp_sso` module on it (`workspace/legacy-local/activate-module.mjs`, idempotent: the bind-mounted module does nothing without its `tblmodules` row), applies erp-api's node-owned schema, then waits for Nginx to answer on both `/api/v1/health` and `/status`. `node scripts/local-down.mjs` stops it. `--dry-run` prints the commands without running anything; `--no-build` reuses the last images.

**The node-owned schema step (ADR-0036).** After the import marker and before the health waits, `local-up` runs `corepack yarn db:apply` in `../erp-api`, which applies every file in `erp-api/prisma/sql/` in filename order through `prisma db execute`. Those files hold the forward-only DDL for tables the new system creates rather than inherits — `tblidentity_audit` is the first (ADR-0034 decision 3) — which the client's dump does not contain, so they do not exist after an import. It runs *after* the import check on purpose: the dump import drops and recreates the whole database, so anything applied earlier would be wiped. Every statement is `CREATE TABLE IF NOT EXISTS`, so a second run changes nothing; a failure stops the bring-up rather than surfacing later as a missing table at runtime. Phase 5 replaces this with migrations.

A second run is a no-op unless a source file changed. Two things make that true, both learned the hard way: the script sets `BUILDX_NO_DEFAULT_ATTESTATIONS=1` (BuildKit's default provenance attestation is timestamped, so a fully cached rebuild still produced a new image ID and Compose recreated api, web and legacy on every run), and `nginx` declares `depends_on: … restart: true` on its three upstreams (nginx resolves upstream names once at start; when an upstream container is recreated with a new IP, Compose now restarts nginx so it re-resolves instead of answering 502).

### Web dev mode (hot reload for erp-web)

The `web` container runs a production build, so every erp-web change needs `local-up` again (a rebuild). While you build screens, use web dev mode instead:

```bash
node scripts/local-up.mjs --web-dev    # the stack without the web container
node scripts/web-dev.mjs               # in a second terminal: next dev on port 3000; leave it running
```

Then open <http://localhost:8088> as usual. A saved change in erp-web shows in the browser within seconds, logged in, against the real api and Perfex. Never open `localhost:3000` directly: the login cookie and the relative `/api/v1` calls only work behind Nginx's one origin. Ctrl+C stops the dev server; `node scripts/local-up.mjs` (no flag) brings the web container back.

How it works: `compose/local.web-dev.yml` leaves `web` out of `up`, drops it from nginx's `depends_on`, and gives nginx `extra_hosts: web:host-gateway`, so `upstream node_web { server web:3000; }` reaches the laptop's port 3000 without changing `default.conf` (nginx reads `/etc/hosts` before Docker's DNS). `--web-dev` also stops and removes a `web` container left from a normal run. Hot reload uses a websocket on `/_next/hmr`, which has its own location in `default.conf` (the shared `proxy-common.conf` clears `Connection`, which would drop the upgrade); outside dev mode that path answers 404. `scripts/web-dev.mjs` refuses to start while the `web` container still runs or when nothing answers on 8088. Verified 2026-10-19 with Next 16.3: pages, assets and the `/_next/hmr` websocket (101) through Nginx, and a saved message-file change visible on the next request with no rebuild.

Published ports: 8088 nginx, 8080 legacy direct, 33061 MySQL, 63791 Redis, 11025 and 18025 Mailpit, all bound to `127.0.0.1` only. `api` and `web` publish nothing; reach them through Nginx. Redis runs with AOF on (`--appendonly yes --appendfsync everysec`, named volume `redisdata`) because DB 1 holds auth sessions (ADR-0005: a cache flush must never log anyone out); DB 0 is cache; it is loopback-only and has no password; `requirepass` and a separate auth instance are Phase 5. The local MySQL runs with an explicit `--max-connections=60` (set in `workspace/legacy-local/docker-compose.yml`, where the service is defined) so the pool arithmetic below is tested against a known number, not MySQL 8's default 151.

## Pool budget

ADR-0031 §4: every consumer of the shared MySQL declares its pool size, and the sum must fit under the server's limit with headroom:

```text
replicas × per-replica + workers × per-worker + legacy's own pool < max_connections − headroom
```

Filled in for the local stack:

| Consumer | Per instance | Instances | Connections |
|---|---|---|---|
| erp-api container (`POOL.db.api`; `connection_limit=10` in `env/local/templates/api.env.tmpl`) | 10 | 1 | 10 |
| erp-api on the host (`api.host.env.tmpl`: `test:int`, `start:local`, Prisma CLI; `connection_limit=5`) | 5 | 1 | 5 |
| erp-api worker container (`POOL.db.worker` is 5 in code; `connection_limit=4` in `env/local/templates/worker.env.tmpl`, the local budget) | 4 | 1 | 4 |
| legacy Perfex (one non-persistent mysqli connection per concurrent PHP request; bounded locally by Apache's prefork workers) | — | — | ≤ 30 (assumption) |
| **Sum** | | | **49** |
| MySQL `max_connections` − headroom (`--max-connections=60` in `workspace/legacy-local/docker-compose.yml`; 10 for root, healthcheck, `mysqladmin`, ad-hoc clients) | 60 − 10 | | **50** |

49 < 50, so the budget holds. Where each number comes from: the per-instance sizes are `POOL.db.*` in `erp-api/src/shared/config/timings.ts`; the rendered `DATABASE_URL` carries the size as `?connection_limit=` (the templates above), and erp-api appends `pool_timeout`, `connect_timeout` and `socket_timeout` from `TIMINGS.db`: timings are code, the pool size is the deployment's budget; the server limit is the `--max-connections` flag. "legacy ≤ 30" is an assumption for the local stack, stated as such: Perfex opens no persistent connections, so its share is the number of PHP requests in flight, which the local Apache prefork configuration bounds. Phase 5 repeats this table per environment against cPanel's `max_user_connections`; `corepack yarn check:db` in erp-api fails when the rendered host URL carries no `connection_limit`.

## Where legacy comes from

The local stack lives in `erp-infra/compose/local.yml` per ADR-0007, and **`erp-infra/legacy-local` holds the legacy stack and is included by relative path** (`../legacy-local/docker-compose.yml`, with `project_directory` and `env_file` pointing at the same folder). Reasons:

- ADR-0011 fixes the sibling layout, so the relative path is stable on every workstation and runner.
- `setup.mjs` and `reset-password.mjs` live in that folder.
- legacy-local is a learning copy of a system we cannot deploy (ADR-0024), not infrastructure. erp-infra owns the composition, not the legacy image.

When wave minus one becomes real, Phase 5 moves the legacy service definition into `erp-infra/base/compose/legacy.yml`. The legacy services are named `legacy` and `legacy-db` (ADR-0025 names the transitional system `legacy`); those names are the Nginx upstream and the api's `DATABASE_URL` host. Running `docker compose` inside `workspace/legacy-local` alone still works under the same project name; it may warn about orphan containers (api, web, nginx, redis), which is expected.

## Real staff photos locally (UAT only)

**Why.** The client's dump carries the `tblstaff.profile_image` names but no files, and `uploads/staff_profile_images/` in the legacy tree holds only `index.html`. Until the client's folder is mounted, every staff photo URL answers 404 locally and the web shows its placeholder instead (the broken-image fallback of plan 03.2-22).

**Where the files come from.** The client's host, `public_html/uploads/staff_profile_images/` (one folder per staff id, each holding the `small_` and `thumb_` copies Perfex writes), fetched by the lead. Keep them OUTSIDE every repository, for example `%USERPROFILE%\erp-local-data\staff_profile_images`. They are personal data: never commit them, and never paste a file name into a log, an issue or a planning file (the names carry staff members' names).

**How.** Write an override file, also outside every repository (for example `%USERPROFILE%\erp-local-data\staff-photos.override.yml`), with the folder as a Windows path in forward slashes (`pwd -W` in Git Bash prints it):

```yaml
services:
  legacy:
    volumes:
      - C:/Users/<you>/erp-local-data/staff_profile_images:/var/www/html/uploads/staff_profile_images:ro
```

Then, from this repository:

```bash
docker compose -f compose/local.yml -f "<path to>/staff-photos.override.yml" up -d legacy
docker compose -f compose/local.yml restart nginx   # nginx resolves legacy once; the recreate gave it a new IP
```

Compose extends the `legacy` service even though it comes from `include:`, so no standalone run is needed. Check: open <http://localhost:8088/setup/staff> and see the photos, or `curl -I` one photo URL the api answers (`profileImageUrl`, already percent-encoded) through `http://localhost:8088` and expect `200` with `Content-Type: image/jpeg`.

**Why a read-only mount and not `docker cp`.** The container's web root IS `../erp-legacy/public_html` (a bind mount), which nobody edits: erp-legacy is read-only for us, so `docker cp` into `/var/www/html/uploads` would write the photos into it. The mount is nested and read-only, the way `modules/erp_sso` is mounted, over a folder that already exists in the tree, so nothing is written on the host. While it is in place Perfex cannot upload a new staff photo, which is expected for a UAT check.

**Undo.**

```bash
docker compose -f compose/local.yml up -d --force-recreate legacy
docker compose -f compose/local.yml restart nginx
```

Or run `node scripts/local-up.mjs`, which recreates `legacy` from `compose/local.yml` alone, without the override.

A host behind a proxy sets `set_real_ip_from` and `real_ip_header` so `auth_login` sees each client; local needs none.

**Wave 0 (Phase 1.3) additions.** The three legacy prefixes `/api/auth/`, `/api/attendance/`, `/api/face/` are the Flutter attendance app's HS256 API and stay on Perfex until Phase 1.4 migrates them to Node; each location carries a comment naming ADR-0030 and must not be pointed at `node_api` (Node's own auth lives under `/api/v1/auth/`, a different prefix by construction). `/timesheets/api/*` is the timesheets module's token issuer, signed with a vendor default key: it answers `410` with `{"code":"ERP-LEGACY-0410",…}` (ADR-0030 decision 3; reversible by deleting the block). `GET /admin/authentication` is redirected to the Next.js `/login` (ADR-0030 decision 1); `?legacy=1` is the escape hatch that keeps the Perfex form reachable for two-factor accounts and support, the form's own POST and `/forgot_password` stay legacy; `/admin/authentication/logout` is three-way like it (ADR-0038). The redirect uses `absolute_redirect off` so the `Location` is the relative `/login`: an absolute one would be built from `$host`, which has no port. Rate limiting on `POST /api/v1/auth/login` is the first brute-force control; erp-api's Redis lockout is the second.

**Keep-alive contract (ADR-0031 §4).** `upstream node_api` sets `keepalive_timeout 60s`, which must stay below erp-api's `fastify.keepAliveTimeoutMs` (65 s) in `erp-api/src/shared/config/timings.ts` so Nginx closes an idle upstream socket before Fastify does — change both together, or the reverse order produces intermittent 502s.

**Compression (ADR-0031 §6).** Api locations include `snippets/proxy-api.conf` (`gzip off`, `Accept-Encoding` passed through) because the api compresses its own responses; Nginx gzips legacy and static (`gzip on` at the top of `default.conf`), and never re-encodes the web upstream's already-encoded bodies.

**Wave 1 (Phase 3.1, W1-06) additions.** Perfex stops managing staff, roles and permissions. Three shapes were needed and the renderer in Phase 5 inherits all three:

- **a redirect with an id capture.** `/admin/staff/member/7` → `302 /setup/staff/7` (`/staff/7` until plan 04.2-29) needs a regex `location` and `$1`, which the `/admin/authentication` precedent does not exercise. The character class is digits only, so nothing but digits reaches the `Location`; with `absolute_redirect off` the `Location` stays relative and `:8088` survives (the same port loss the login block explains).
- **a three-way path.** A plain `GET` redirects to the Node screen, `?legacy=1` reads the Perfex page (ADR-0030's escape hatch) and **any other method is refused** — Nginx cannot select a `location` by method, so the decision is three `map`s beside `$erp_login_redirect` (which is reused as written: it means "a plain `GET` without `?legacy=1`" and is generic despite its name). `$erp_identity_write` keys on the method **alone**, so `?legacy=0` can never turn a `POST` into a read.
- **a refusal, not a rewrite.** Every closed write path `return`s `403` with `{"code":"ERP-LEGACY-0403",…}` from `snippets/refuse-identity-write.conf`, and never proxies or redirects: proxying a form `POST` to `node_web` answers with Next's 404 page (reads as "the page moved", not "your change was refused"), and redirecting one makes the browser re-issue it as a `GET`, so the write silently does not happen and the screen looks like it succeeded.

Perfex's write paths for `tblstaff`, `tblstaff_permissions` and `tblroles` are closed because Node owns them (ADR-0034 d.1): a Perfex screen writing them keeps no audit row (d.3), bypasses the admin-only granting gate (d.2) and leaves Node's `auth:perm:{staffId}` snapshot stale. That covers the core screens **and** the seven modules' 15 permission-write methods in all four CI3 URL forms: `MX_Router` serves every module method under `/admin/<m>/<m>/<x>`, `/admin/<m>/<x>`, `/<m>/<m>/<x>` and `/<m>/<x>`, so one `~*` regex closes all four. The modals still open: `permission_modal`, `*_permission_table`, `role_changed` and `hr_role_changed` are reads and are deliberately not matched. `hr_profile`'s own member screens (`add_edit_member`, `delete_staff`, `update_staff_profile`, with `member_modal`) also write `tblstaff`, and the member form rewrites a member's role and permission set too (finding 6); W1-06 left them open as that module's daily screens, and nothing in `default.conf` closes them.

Four findings for the Phase 5 renderer, all learned here:

1. **`/_next/` must go to web.** A migrated page's CSS, JS chunks and RSC payloads are requested under `/_next/`, not under the page path. Without an explicit location they fall through to legacy and the page renders unstyled or not at all. The routing renderer in Phase 5 must emit `/_next/` (and any `basePath`) for web automatically, not per module.
2. **Forward `Host` with the port.** `snippets/proxy-common.conf` sets `proxy_set_header Host $http_host;` (not `$host`). Perfex derives `APP_BASE_URL` from `HTTP_HOST`; with `$host` the port is stripped and every legacy redirect goes to `http://localhost/...` instead of `http://localhost:8088/...`.
3. **A retired legacy path is three decisions, not one**, and the generator needs all three per path: the Node screen it redirects to, whether `?legacy=1` may still read the old page, and whether a write there is refused. `routing.yml`'s `legacy_paths` is a flat list today; rendering W1-06 by hand needed a redirect target, a read/write split and a list of sibling paths that must NOT move (a read the other modules still call, a delete that writes 40 tables Node does not own). The awkward ones for a generator are the id capture (the target is a template, not a literal) and the module URL fan-out (one method, four URL forms, and the module name repeated inside the path).
4. **A closed legacy path must be closed under every URL CI3 routes to it** (quick 260929-hdy, found 2026-09-29). PHP method names are case-insensitive (on a case-insensitive disk so are the directory and controller segments), and CodeIgniter 3 routes `/index.php/<p>`, `/index.php?/<p>`, `/?/<p>` and `/index.php/?/<p>` to `<p>` and drops raw `..` segments, so the case-sensitive `^~` refusals were reachable from Perfex (`/admin/roles/DELETE/<id>`, `/index.php?/admin/roles/delete/<id>`, `/admin/roles/../delete/<id>`). The renderer must emit two things: the server-level unwrap, once, at the top of the server block (every location, today's and every later wave's, then answers an alias as it answers `<p>`; a raw `..` or a malformed query form is `400`; a nested alias is left for Perfex), and `~*` on every refusal. A per-location `index.php` prefix is unnecessary and would drift. `scripts/verify-wave0.mjs` 17m to 17t prove every form without a session.

## Env files

Templates live in `env/local/templates/` (`api.env.tmpl`, `api.host.env.tmpl`, `web.env.tmpl`) with `{{DB_USER}}`, `{{DB_PASSWORD}}`, `{{DB_NAME}}` placeholders. `scripts/render-local-env.mjs` renders them into gitignored `env/local/*.env` from the legacy stack's generated credentials (`legacy-local/.env`, random per machine, never a production value). The renderer percent-encodes the password for the `DATABASE_URL` and never prints a value.

A second source is computed by the renderer itself: on first run it generates an RSA-2048 signing key into `env/local/auth-jwt-private.pem` (PKCS8, mode 0600, gitignored by `env/local/*.pem`) and renders its base64 as `{{AUTH_JWT_PRIVATE_KEY_PEM_B64}}`; later runs print `reusing env/local/auth-jwt-private.pem`. `node scripts/render-local-env.mjs --rotate-jwt-key` deletes and regenerates it — every local session becomes invalid, which is the point of rotating; recreate the api container afterwards (`node scripts/local-up.mjs`) so it loads the new key. **No `.pem` and no rendered `.env` is ever committed** (ADR-0014); `git -C erp-infra ls-files | grep -iE 'jwk|pem|key'` must return nothing but templates and scripts.

## Notes for Windows and Git Bash

- Every text file is LF (`.gitattributes`: `* text=auto eol=lf`); the scripts write `\n`.
- `docker run -v` from Git Bash needs a Windows path and no MSYS path mangling: `MSYS_NO_PATHCONV=1 docker run --rm -v "$(pwd -W)/nginx/local:/etc/nginx/conf.d:ro" ...`.
- `nginx -t` resolves upstream hostnames at test time. To syntax-check `nginx/local/default.conf` without the stack running, give the test container aliases: `docker run --rm --add-host api:127.0.0.1 --add-host web:127.0.0.1 --add-host legacy:127.0.0.1 -v ... nginx:1.27-alpine nginx -t`.
- `docker compose -f compose/local.yml config` prints the merged file **with env_file values interpolated**; do not paste its output anywhere.
